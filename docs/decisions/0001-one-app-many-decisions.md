# One Prism application holds every community decision app

## Context and Problem Statement

The community model has many decisions to make: the TOC lifecycle, three
repository norms, the Code of Conduct ladder, contribution attribution, the
Discord read policy, observation admission and one indicator per CHAOSS metrics
model (27 today). The Prism-DevRel builder turns one `prism/prompt/1` into one
whole template instance: the app module and its proofs, every facet module,
`lexlean.toml`, the claim rows, the page. The template verifies and publishes
`app/` alone (`just vv` runs `prismpm --project app verify`; `bootstrap.yml` is
a universal policy file bound by `template.lock`). How does one repository hold
all of these apps so that every one of them is verified and published?

## Decision Drivers

* Every app's behavior is verified by the gate: its theorems by the Lean
  kernel and its acceptance vectors replayed in a compiled guest.
* Every app is published, so a visitor can run it.
* ISO/IEC/IEEE 42010:2022 describes one entity of interest with one
  architecture description; the entity here is the Foundation's community.
* No universal template file is edited (AGENTS.md, template boundary).
* The model is generated, never hand-written, and regenerated by one command
  (Alex's rules: mechanize, generate, fewest tokens).

## Considered Options

* One prismpm project per app, each in its own directory.
* One prismpm project, the builder emitting a module set into the one `app/`,
  with a generated router as its root application.

## Decision Outcome

Chosen option: **one prismpm project, a module set and a router**, because it
is the only option in which the template's own gate verifies and publishes
every app, and in which the facets form one architecture description.

* `apps/*.prompt.json` holds one prompt per decision. `apps/indicators.mjs`
  writes the indicator prompts from `chaoss/register.json` and lists every
  prompt in `apps/set.json` (`prism/prompt-set/1`).
* `node builder/cli.mjs build-set apps/set.json --out .` (afflom/prism-devrel)
  writes each app's module pair (`app/src/<App>.lex.tex`, `<App>Proofs`), the
  router `app/src/UorCommunityDecisions.lex.tex`, and one set of facet
  modules. The router is the project's root `application`: its guest reads an
  app's name, a space, and answers the rest exactly as that app's `dispatch`
  does. For each app, the first of its acceptance vectors that gives each of
  its answers, and the first it refuses, prefixed with its name, are the
  router's, so `prismpm verify` replays every path through every app's
  compiled decision in the one guest.
* The guest is one Rust crate, which names a compiled declaration by its last
  component, so each app's declarations take its module's name
  (`uorRepoFilesJudge`, `UorRepoFilesRequest`), and every reference in its
  proofs, the facets and the claims is renamed with them.
* The facets describe the one system. Each app's records keep their own names
  (the app's module name follows each record's prefix). What the apps share is
  one record: stakeholders by name, the platform components (browser, build,
  Pages, source) and components the prompts name alike, the edges between
  them, and the ISO/IEC 25010 characteristics and subcharacteristics.
* Each app's claims take the initials of every word of its name (`URF-01`,
  `URS-01`, `UTL-01`), so apps whose two-letter prefixes would collide keep
  distinct ids; the facet theorems are the set's (`UCD-01` to `UCD-03`). Rows,
  entrypoints and files the set does not own (the CHAOSS register, `CC-*`,
  `FR-01`) are kept.
* `apps/build.sh` runs the whole regeneration: indicators, `build-set`,
  `lexlean fmt`, `lexlean lock`, `check-model --write`.

### Consequences

* Good, because every app is verified and published by the unmodified
  template gate, and one page runs every decision.
* Good, because a new decision is one prompt, and a new CHAOSS metrics model is
  no prompt at all: the register brings it.
* Good, because shared stakeholders and components are one record, so the
  stakeholder views (workstream 6) and STRIDE over every component (workstream
  7) see the system, not 27 copies of it.
* Bad, because one guest's request bound is the largest app's plus its name,
  and every change rebuilds the one holo. The builder is deterministic and
  `prismpm verify` reuses a kept proof only for identical inputs, so this costs
  compute, not correctness.
* Bad, because the router itself carries no theorem; its behavior is held by
  the acceptance vectors replayed in the guest, which the gate fails on any
  mismatch.
* Bad, because the SDK's browser oracle keeps at most 64 KiB of replay
  evidence for one guest, so the router replays one vector per answer of each
  app (141 for 28 apps), not every vector a single-app build would. Each
  app's behavior is still proved by the Lean kernel for every request; the
  vectors check that the compiled guest computes what was proved.
* Neutral, because LexLean links a module through JSON of bounded depth and
  reads application metadata as closed terms, so a list longer than 32 items
  is written in parts, each part's tail a reference to the next.

### Confirmation

`just vv` in the SDK image `prismpm.lock` pins verifies every app's theorems
and replays the router's vectors. `node <builder> build-set apps/set.json
--out . --check` and `node apps/indicators.mjs --check` exit 1 when a
committed file differs from what the prompts and the register generate.

## Pros and Cons of the Options

### One prismpm project per app

* Good, because the builder already writes it, unchanged.
* Bad, because the template verifies and publishes `app/` alone: every other
  project would be neither verified by `just vv` nor published, unless
  `bootstrap.yml`, a universal policy file, were edited.
* Bad, because each app would carry its own architecture description of the
  same community, and the descriptions could disagree.

### One prismpm project, a module set and a router

* Good, because the template gate is unchanged and covers everything.
* Good, because the facets are one 42010 architecture description.
* Neutral, because it needs a builder verb (`build-set`), contributed to
  afflom/prism-devrel, that leaves single-app `build` unchanged.

## More Information

* Format: MADR 4.0.0 (https://adr.github.io/madr/).
* Patterns: OMG DMN 1.5 (hit policy FIRST), OASIS XACML 3.0, OMG UML 2.5.1.
* Indicators: ISO/IEC 15939. The CHAOSS models publish no decision criteria
  over their metrics' values, so each indicator decides only what the source
  supports: whether every base measure has an observation admitted by
  `uor-observation-admission`, how many were refused, or none was observed. A
  model member the register cannot match is counted refused (CC-03), so that
  model is an open claim until CHAOSS releases it.
